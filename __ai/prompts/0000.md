# Specification: `devzy` CLI Tool — Initial Version

## 1. Objective

Build `devzy`, a Bun-based TypeScript CLI for aggregating developer activity across version-control and project-management providers, managing provider configuration, and checking provider health.

The initial release must be usable from a fresh installation without live API credentials by using deterministic mock providers. The architecture must allow live adapters to be added without changing command handlers or provider-independent business logic.

Priorities, in order:

1. Correctness and predictable behavior.
2. Clear separation of concerns and small, domain-specific interfaces.
3. Safe, validated configuration and secret handling.
4. Deterministic automated tests.
5. Useful terminal output and actionable errors.
6. Incremental support for real providers.

Do not claim that a live integration is implemented unless it makes real requests to that service and has appropriate tests. Clearly label mock data.

## 2. Scope

### 2.1 Version-one capabilities

- Global and command-specific help.
- Git activity reporting.
- Task activity reporting.
- Combined activity reporting.
- Extensible, shared reporting filters for dates, email, provider, repository, and task status.
- Provider listing and interactive provider setup.
- Health checks for configured, enabled providers that support health checks.
- YAML configuration with environment-variable overrides.
- Deterministic mock implementations.
- Unit and CLI integration tests.
- README and example configuration.

### 2.2 Provider scope

The architecture should accommodate these provider types:

- **Git:** GitHub, GitLab, Bitbucket.
- **Tasks:** Jira, Linear, ClickUp, OpenProject.
- **Health:** health-check targets or providers, if implemented as a distinct category.

For the initial release, provide mock implementations for at least:

- `GitHubGitProvider`
- `GitLabGitProvider`
- `JiraTaskProvider`
- `LinearTaskProvider`

Other listed providers may be represented as known provider types with an explicit “not implemented” status, but must not be presented as working live integrations. If their mock adapters are implemented, they must follow the same contracts and test requirements.

Clarify in the implementation whether `health` is a distinct provider category or a capability supported by Git and task providers. Do not require every provider to implement health checks unless that is part of its actual contract.

## 3. Technology and quality requirements

- Runtime: Bun.
- Language: TypeScript with strict compiler settings enabled.
- Configuration format: YAML.
- Use a maintained CLI argument-parsing library or Bun-compatible parsing approach. Keep command parsing separate from business logic.
- Use a maintained YAML parser and validate parsed configuration against an explicit schema.
- Use the built-in Bun test runner unless a concrete need justifies another framework.
- Add scripts for development, tests, type checking, linting, and formatting.
- Use asynchronous APIs and avoid blocking I/O where practical.
- Do not add dependencies without a clear purpose.
- Do not use `any` to bypass type errors except at a narrowly isolated external boundary with a documented reason.
- Do not leave TODO-only implementations, fake success responses, or unimplemented command handlers behind a success exit code.
- All commands must have meaningful behavior in mock mode.

Document the minimum supported Bun version and all required setup commands in the README.

## 4. CLI command surface

Implement the following commands:

```text
devzy help
devzy --help
devzy pm help
devzy pm git
devzy pm tasks
devzy pm all
devzy providers
devzy providers help
devzy providers list
devzy providers add
devzy health
devzy health show
devzy health help
```

`devzy providers` is an alias for `devzy providers list`. `devzy health` is an alias for `devzy health show`.

Unknown commands and invalid arguments must display a concise error and relevant help guidance. Use exit code `0` for successful commands and nonzero exit codes for failures. Send errors and diagnostic messages to stderr; send normal report output to stdout.

Support a non-interactive mode for automation. Interactive prompts must not run when stdin is not a TTY; instead, require explicit arguments or report which values are missing.

### 4.1 `devzy pm git`

Display a table of Git activity aggregated across configured, enabled Git providers.

At minimum, include:

- Contributor name.
- Commit count for the reporting period.
- Provider or repository coverage where available.

Do not claim to report additions, deletions, pull requests, or other metrics unless the provider contract retrieves and defines those metrics.

### 4.2 `devzy pm tasks`

Display normalized task activity aggregated across configured, enabled task providers.

At minimum, include:

- Contributor name.
- Completed task count.
- In-progress task count.
- In-review/testing task count.

Use consistent column names and ordering across providers.

### 4.3 `devzy pm all`

Display a unified contributor table containing the supported Git and task metrics. Use a canonical identity model to combine records from multiple providers.

Do not merge users automatically based only on display name. If identities cannot be matched confidently, retain separate entries and make the unmatched status visible or document the behavior.

Do not invent a composite “activity score.” The initial release should sort by a documented primary metric or use an explicitly configured formula. If a composite score is implemented, document its formula, weights, treatment of missing data, and tie-breaking behavior.

### 4.4 Reporting periods and sorting

All reporting commands must use a consistent, explicit reporting period. The date filter names are `--dt-since` and `--dt-to`. Provide a documented default (for example, the previous 30 days) and a way to override it using CLI options such as:

```text
devzy pm git --dt-since 2026-01-01 --dt-to 2026-01-31
devzy pm tasks --dt-since 2026-01-01 --dt-to 2026-01-31
devzy pm all --dt-since 2026-01-01 --dt-to 2026-01-31
devzy pm all --dt-since 2026-01-01 --dt-to 2026-01-31 --email dev@example.com
devzy pm git --provider github --repo org/project --email dev@example.com
devzy pm tasks --status completed --provider jira
```

Treat the example dates as inclusive calendar dates in a documented timezone. Validate date formats and reject an end date earlier than the start date. Use one shared reporting-period model across commands and provider interfaces.

Define stable sorting and tie-breaking rules. Empty results must produce a useful message rather than a misleading empty ranking.

### 4.5 Shared, extensible filtering

Implement a reusable filtering system for reporting commands. Filters must be parsed and validated at the CLI boundary, represented by a typed shared filter/query model, and applied consistently by the aggregation services. Do not duplicate filter logic inside each command.

Support these filters in version one:

- `--dt-since <YYYY-MM-DD>`: inclusive start date.
- `--dt-to <YYYY-MM-DD>`: inclusive end date.
- `--email <email>`: include activity associated with the specified email address.
- `--provider <id-or-type>`: limit results to a configured provider instance ID or documented provider type.
- `--repo <owner/name>`: limit Git reports to the specified repository when supported by the provider.
- `--status <status>`: limit task reports to one or more normalized task states (`completed`, `in_progress`, `in_review`).

Apply date and email filters to `pm git`, `pm tasks`, and `pm all` where the underlying data supports them. Apply `--repo` only to Git-related reports and `--status` only to task-related reports. Reject incompatible filters with an actionable error rather than silently ignoring them.

Filtering rules:

1. `--dt-since` and `--dt-to` are optional independently. If omitted, use the documented default reporting period. Reject malformed dates and a start date later than the end date.
2. Treat both CLI dates as inclusive calendar dates in a documented timezone. Internally, it is acceptable to represent the interval as a half-open range ending at midnight after `--dt-to`, provided this conversion is centralized and tested.
3. Email matching must be case-insensitive and whitespace-trimmed, and must use exact normalized email matches rather than substring matches. Do not infer identity from a display name.
4. For task activity, an email filter may be applied only when the task provider supplies an email or an explicit identity mapping connects the task account to that email. Do not silently drop task results or guess matches when the required identity data is unavailable; report the limitation or return a clear validation/unsupported-filter error according to a documented policy.
5. Allow repeatable filters where they are useful. For example, repeated `--email` values mean “match any listed email,” repeated `--provider` values mean “include any listed provider,” and repeated `--status` values mean “match any listed status.” Document this OR behavior within a filter category.
6. Different filter categories combine with AND semantics. For example, `--provider github --email dev@example.com` means activity from the selected provider that also matches the email.
7. A filter must never broaden the result set silently. If a provider cannot enforce a filter remotely, apply it to normalized data locally when sufficient data is available; otherwise return an explicit unsupported-filter result.
8. In combined reports, apply filters consistently before final aggregation where possible. Preserve enough provider and identity metadata to ensure filtering does not merge or discard contributors incorrectly.
9. Include active filters in report context or a concise header so users can tell which scope was applied. Do not display secret configuration values.
10. Make the filter model extensible so future filters (for example, team, label, project, branch, or task assignee) can be added without rewriting each command.

The help output and README must document filter applicability, defaults, repeated-value behavior, date semantics, and examples. Add tests for combinations of filters, incompatible filters, missing identity data, inclusive date boundaries, and empty filtered results.

### 4.6 `devzy health show`

Run health checks for configured, enabled providers that implement the health-check capability.

Display a table with provider name, category, status, and diagnostic message. Use a timeout for each check. Catch failures per provider so one failed check does not prevent the remaining checks from running.

Distinguish healthy, unhealthy, timed out, and not checked/not supported states where relevant. Never print credentials or other secrets in diagnostic messages. Define and document the command's exit-code behavior when one or more checks fail.

### 4.7 `devzy providers list`

List provider types known to the application separately from configured provider instances. Group configured instances by category (`git`, `tasks`, and `health` if health is a distinct category).

For each configured instance, display its name or ID, type, enabled state, and implementation mode (`mock`, `live`, or `not implemented`) where applicable. Never show secret values.

### 4.8 `devzy providers add`

Provide an interactive flow that:

1. Lists provider types supported by the current build.
2. Explains whether the selected type is mock-only or has a live adapter.
3. Collects required configuration values.
4. Validates values before saving.
5. Allows the user to cancel without changing the configuration.
6. Saves the entry without overwriting unrelated configuration.
7. Confirms the saved provider by a non-secret identifier.

Do not ask for credentials that a mock provider does not need. For live providers, collect only fields required by that adapter, such as a token, base URL, workspace, organization, or project identifier.

When a provider type is known but not implemented, explain that clearly and do not save an entry that would be silently ignored.

## 5. Configuration

### 5.1 Configuration locations

Support these configuration sources:

- Default user configuration: `~/.config/devzy/config.yaml`.
- Optional project configuration: `./devzy.yaml`.
- Explicit path override: `devzy_CONFIG_PATH`.

Document the exact behavior when more than one file exists. Use a deterministic rule, such as loading the default user file first and then merging the project file, with `devzy_CONFIG_PATH` selecting an explicit configuration file instead of relying on implicit discovery. Do not silently merge files unless that behavior is documented and tested.

### 5.2 Precedence

Use and document a single precedence model:

1. Built-in defaults.
2. Configuration file values.
3. Environment-variable overrides.
4. Explicit CLI options, when a command supports an equivalent setting.

For settings with no environment variable, retain the file value. An unset environment variable must not erase a configured value. Define the supported environment variables in the README and example configuration.

Support provider-specific credential variables where applicable, such as `GITHUB_TOKEN` and `JIRA_API_KEY`. Map them explicitly to known provider instances or documented provider defaults; do not guess which configured instance a credential belongs to when several instances are present.

### 5.3 Schema and persistence

Define typed configuration models and validate the fully resolved configuration before use. Report the configuration path and actionable validation errors without printing secret values.

Provider entries should have stable IDs, a provider type, a display name, an enabled flag, and provider-specific configuration. Keep secrets separate from non-secret settings where practical, and allow credentials to be supplied through environment variables.

When writing configuration:

- Create parent directories when necessary.
- Use restrictive file permissions where supported.
- Write atomically where practical to avoid corrupting a valid file.
- Preserve unrelated provider entries and user settings.
- Validate the resulting configuration before replacing the existing file.
- Do not log or display tokens, passwords, API keys, or authorization headers.

Never commit real credentials or a populated personal configuration file. Provide a safe example file with placeholder values only.

## 6. Domain models and provider interfaces

Keep provider-independent domain models separate from CLI presentation and vendor-specific response formats.

### 6.1 Base provider

The base contract should contain only common provider metadata, for example:

```typescript
export type ProviderType = "git" | "tasks" | "health";

export interface BaseProvider {
  id: string;
  name: string;
  type: ProviderType;
}
```

Use literal or discriminated types where they improve correctness. Avoid putting unrelated methods on the base interface.

### 6.2 Health-check capability

Model health checking as a separate capability if not every provider supports it:

```typescript
export interface HealthCheckResult {
  ok: boolean;
  message: string;
}

export interface HealthCheckable {
  healthCheck(): Promise<HealthCheckResult>;
}
```

The health command must check whether a provider supports this capability before attempting a check.

### 6.3 Shared reporting period

Define a shared reporting-period type used by Git and task providers:

```typescript
export interface ReportingPeriod {
  since: Date;
  until: Date;
}
```

Document whether `until` is exclusive internally. Prefer a single consistent internal convention and convert CLI date inputs at the boundary.

### 6.4 Git provider

Define `GitProvider` as a domain-specific interface. It should expose a method similar to:

```typescript
export interface GitCommitStats {
  authorName: string;
  authorEmail?: string;
  commits: number;
  providerUserId?: string;
  repository?: string;
}

export interface GitProvider extends BaseProvider {
  type: "git";
  getCommitStats(
    period: ReportingPeriod
  ): Promise<GitCommitStats[]>;
}
```

Adjust the model if necessary to support aggregation across repositories and provider instances. Define whether returned rows are per contributor, repository, or both, and ensure aggregation does not double-count the same row.

### 6.5 Task provider

Normalize vendor-specific task statuses into these internal buckets:

- `completed`
- `in_progress`
- `in_review`

Map the user-facing label for `in_review` to “In review / testing” if desired. Document how vendor statuses map to these buckets and how unmapped statuses are handled. Do not silently classify an unknown status as completed.

Use a model similar to:

```typescript
export interface UserTaskStats {
  username: string;
  providerUserId?: string;
  completed: number;
  inProgress: number;
  inReview: number;
}

export interface TaskProvider extends BaseProvider {
  type: "tasks";
  getUserTaskStats(
    period: ReportingPeriod
  ): Promise<UserTaskStats[]>;
}
```

The actual implementation may use richer shared identity types, but provider-specific identifiers must be preserved until identity resolution is performed.

### 6.6 Identity resolution

Create a provider-independent identity model for contributors. Support explicit mappings between canonical team-member IDs and provider-specific identifiers, such as usernames, account IDs, and verified email addresses.

Rules:

- Never merge people based only on display names.
- Prefer explicit mappings and stable provider account IDs.
- Normalize email addresses carefully and document matching rules.
- Keep unmatched identities separate.
- Make ambiguous matches visible rather than guessing.
- Add tests for duplicate names, aliases, missing emails, and cross-provider matches.

## 7. Provider registry and dependency direction

Implement a provider registry or factory that maps supported provider types to constructors and metadata. The registry should distinguish:

- Known provider types.
- Available mock adapters.
- Available live adapters.
- Configured provider instances.
- Enabled provider instances.

Commands should depend on application services and provider interfaces, not instantiate vendor-specific classes directly. Business logic must not import CLI table-rendering or prompt modules.

Keep provider-specific API code inside each adapter. Convert vendor response formats to shared domain models at the adapter boundary.

## 8. Mock and live modes

Mock mode must work without credentials and use deterministic fixture data. The same fixture inputs must produce the same outputs so tests and examples are reproducible.

Requirements:

- Clearly label reports as mock/demo data.
- Do not mix mock data with live data in a report unless the user explicitly requests it and the output identifies each source.
- Make mock versus live mode explicit in configuration or provider registration.
- Do not silently fall back from live to mock mode after an authentication or network error.
- Use realistic but fictional contributor names and records.
- Ensure fixture dates respect the selected reporting period.
- Mock health checks must return predictable results and include tests for both healthy and unhealthy cases.

Live adapters must implement the same interfaces and have provider-specific tests. A live adapter must not be marked as implemented if it only returns fixtures.

## 9. Aggregation and partial failures

Implement provider-independent aggregation services for Git statistics, task statistics, and combined activity. Keep aggregation separate from command handlers.

Define consistent behavior for provider errors:

- Capture errors per provider.
- Do not convert failed requests into zero activity.
- Do not silently omit failed providers from a report.
- Where partial results are displayed, label the report as partial and identify failed providers without exposing secrets.
- Return a nonzero exit code when the command's documented failure policy requires it.
- Continue querying other providers when safe and useful.

Deduplicate only where the available identifiers and documented rules justify it. Do not assume that matching names or matching commit counts imply duplicate records.

## 10. Terminal output and logging

Implement reusable table formatting and terminal logging utilities.

Requirements:

- Consistent column names, ordering, numeric formatting, and sorting.
- Useful empty-state messages.
- Readable output on narrow terminals where practical.
- No secret values in tables, logs, stack traces intended for routine CLI use, or error messages.
- Progress and diagnostic messages go to stderr; report tables go to stdout.
- Support a quiet or non-interactive execution path if useful for automation.
- Keep formatting separate from aggregation and provider API code.

A machine-readable output format such as JSON is optional for the initial version. If implemented, document its schema and ensure diagnostics do not corrupt JSON output on stdout.

## 12. Testing requirements

Use Bun's test runner unless another test framework is justified.

At minimum, test:

### Unit tests

- Configuration loading, precedence, missing files, and malformed YAML.
- Environment-variable overrides and unset variables.
- Configuration schema validation and safe persistence.
- Provider registry lookup and unsupported provider types.
- Git aggregation and task aggregation.
- Task status normalization, including unknown statuses.
- Identity matching, ambiguous identities, and unmatched contributors.
- Reporting-period validation and boundary behavior.
- Filter parsing, filter combinations, repeated values, incompatible filters, and empty results.
- Exact normalized email matching and missing identity data.
- Provider, repository, and task-status filter behavior.
- Ranking order and tie-breaking.
- Health-check timeouts and exceptions.
- Secret redaction in diagnostic output.

### CLI integration tests

- Global and subcommand help.
- Every required command in mock mode.
- Empty report output.
- Invalid command and invalid argument handling.
- Missing or invalid configuration.
- Provider listing and adding.
- Non-interactive behavior.
- Partial provider failures.
- Exit codes and stdout/stderr behavior.

Tests must not require network access or real credentials. Use temporary directories and isolated environment variables for configuration tests. Restore any modified process environment after each test.

## 13. Documentation

The README must cover:

- Purpose and supported capabilities.
- Prerequisites and installation.
- Development commands.
- Configuration paths and precedence.
- Example YAML with placeholder values only.
- Supported environment variables.
- Mock versus live mode.
- Every CLI command with examples.
- Reporting-period semantics and ranking rules.
- Identity matching behavior.
- Error handling and exit codes.
- Which provider adapters are mock-only and which are genuinely live.
- Known limitations and how to add a new provider.

Do not describe future or unimplemented functionality as already available.

## 14. Acceptance criteria

The initial release is complete only when all of the following are true:

1. All required commands and help routes work.
2. A fresh checkout can run all reporting commands in mock mode without API credentials.
3. Mock output is deterministic and clearly labeled.
4. Configuration paths, precedence, environment-variable overrides, and validation are documented and tested.
5. Adding a provider validates the entry and preserves unrelated configuration.
6. Secrets are never printed by normal CLI output or routine error handling.
7. Task statuses are normalized consistently.
8. Cross-provider aggregation follows documented identity rules and does not merge ambiguous identities.
9. Reporting periods, filter syntax and applicability, and ranking/tie-breaking rules are documented and tested.
10. Provider failures are visible and are not represented as zero activity.
11. Health checks handle timeouts and individual provider failures.
12. Unit and CLI integration tests pass.
13. Strict TypeScript checking passes.
14. Formatting and linting pass.
15. The README and example configuration are complete.
16. No command silently reports success when its functionality is unimplemented.

## 15. Implementation workflow and final response

Implement incrementally in this order:

1. Set up Bun, TypeScript, scripts, and tests.
2. Define shared domain models, interfaces, configuration schema, and provider registry.
3. Implement deterministic mock adapters.
4. Implement identity resolution and aggregation services.
5. Implement CLI parsing, commands, tables, and prompts.
6. Add configuration persistence, error handling, and health checks.
7. Add tests and documentation.
8. Run all quality checks and fix failures.
9. Review the implementation for security issues, misleading mock/live behavior, and incomplete requirements.

Before finishing, run the available test, type-check, lint, and format commands. Do not claim a check passed unless it was actually run and passed.

In the final implementation summary, report:

- What was implemented.
- Which provider adapters are mock-only and which are live.
- Commands to install, test, type-check, and run the CLI.
- Any known limitations or deferred requirements.
- Test and quality-check results.

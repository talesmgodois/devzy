# Task: Prepare devzy for production and automated npm publishing

## Objective

Turn `devzy` into a properly packaged npm CLI. It is a Bun + strict
TypeScript CLI that aggregates developer activity from GitHub, GitLab, Jira,
OpenProject and mock providers. The work covers:

- a Node.js-compatible build;
- a verified package tarball;
- CI on GitHub Actions;
- tag-driven publishing to npm through Trusted Publishing (OIDC).

This is an implementation task. Change the code, add the workflows, scripts,
tests and docs, and run the checks. Do not stop at recommendations or sample
YAML. Proceed without asking for approval. Stop only for a genuine blocker,
and in that case finish all independent work and list the blocker.

Do not change CLI behaviour (commands, options, output, exit codes) or the
provider architecture except where this prompt requires it.

## 1. Decisions (apply these; change one only with a stated reason)

1. **Distribution model.**
   - npm users run devzy on **Node.js**; Bun stays the development and test
     toolchain.
   - Build a single ESM entry `dist/devzy.js` with a `#!/usr/bin/env node`
     shebang, e.g. `bun build src/bin/devzy.ts --target=node --format=esm`.
   - Keep `yaml` and `zod` as **external** declared `dependencies`, so
     security updates reach users without a devzy release, unless you
     measure a concrete reason to bundle them.
   - Don't ship source maps, `.d.ts` files or `src/`. There is no
     programmatic API, so add no `exports`/`main` beyond what npm needs.
2. **Minimum Node.js: 22** (`"engines": { "node": ">=22" }`). Node 20 reached
   end-of-life in April 2026, and Trusted Publishing needs a recent
   Node/npm anyway. Verify the exact minimum (e.g. 22.x) against what the
   build actually uses.
3. **Replace `Bun.stringWidth`** with a Node-compatible implementation, for
   example the maintained `string-width` package. Keep the existing table
   tests green and add one for wide (CJK/emoji) characters.
4. **Single source of version.**
   - Inject the `package.json` version at build time (bundler `define`), or
     read it in a way that works both from source under Bun and from
     `dist/` under Node.
   - Remove the hard-coded `VERSION`.
   - Test that `devzy --version` equals `package.json`.
5. **Exit codes.** Replace `process.exit(code)` with `process.exitCode =
   code` so stdout/stderr are flushed when piped. Make sure nothing (open
   readline, timers) keeps the process alive. Add a regression test that
   pipes a large report and checks it is not truncated.
6. **`.env` under Node.**
   - Do **not** add implicit `.env` loading: it would read secrets from any
     directory the user happens to be in.
   - Document the change: under Node, export the variables or use
     `node --env-file=.env $(which devzy) …`.
   - Make sure nothing in tests or docs relies on auto-loading for the
     published build.
7. **Package name: `devzy`.**
   - Check availability with `npm view devzy` (network). If it's taken,
     don't rename the product; use a scoped name (`@<owner>/devzy`) with the
     same `devzy` bin and record that the owner must confirm it.
   - Remove `"private": true` only once the name is settled. If network
     access isn't available, say so.
8. **Release model: tag-driven.**
   - A maintainer bumps the version (`npm version <patch|minor|major>`),
     pushes the commit and the `vX.Y.Z` tag, and the publish workflow
     releases exactly that tag.
   - Release notes come from GitHub's generated notes, grouped by the
     existing Conventional Commit types.
   - semantic-release is out of scope. It would need bot commits and a write
     token, which conflicts with tag/version matching and least privilege.
     Mention it as a possible later step.
9. **Unknown metadata. Don't invent it.** These need the maintainer:
   license, repository URL/owner, homepage, bugs URL, author.
   - Leave them out, or use clearly marked placeholders that a check flags.
   - Don't add a `LICENSE` file without a confirmed license.
   - Make the publish workflow **fail** while `license` or `repository` is
     missing, with a clear message. npm provenance and Trusted Publishing
     both depend on a correct `repository.url`.

## 2. Build, scripts and package contents

Add or adjust these scripts (the names may follow existing style):

| Script         | Does                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| `build`        | Clean `dist/` and build `dist/devzy.js` (shebang, executable bit)        |
| `pack:check`   | Build, `npm pack --dry-run --json`, and assert the file list (allowlist) |
| `smoke`        | Pack, install the tarball into a temp dir **outside the repo**, and run it with **Node** |
| `check`        | Existing checks + `build` + `pack:check` + `smoke`                       |

- Use a `files` allowlist: `dist/`, `README.md`, `LICENSE` (once it exists)
  and `devzy.example.yaml` if the README links to it. `package.json` is
  always included.
- The pack check fails if the tarball contains anything else, in particular:
  `src/`, tests, `__ai/`, `.env*`, `devzy.yaml`, coverage, lockfiles, configs.
- Use `prepack` (or `prepublishOnly`) to build, so a forgotten build can't
  publish stale output. Don't use lifecycle scripts that run on consumers'
  machines (`install`, `postinstall`).
- Keep Biome and `tsc` away from `dist/`.
- **The smoke test** (implement it as a script or a Bun test in its own folder
  that `bun test` does not run by default) installs the packed tarball with
  npm into a fresh temp directory, using a fresh `HOME` and no
  `DEVZY_CONFIG_PATH`. With the installed `node_modules/.bin/devzy` it checks:
  1. `--help` and `--version` (equal to `package.json`) work and exit 0;
  2. `devzy pm all --dt-since 2026-01-01 --dt-to 2026-01-31` works in mock
     mode with the built-in demo config and prints `MOCK DATA`;
  3. `devzy providers` and `devzy health` exit 0;
  4. an invalid `DEVZY_CONFIG_PATH` file exits 4 with a useful message;
  5. an unknown command exits 2 with output on stderr;
  6. it runs with `bun` absent from `PATH`;
  7. no file outside the installed package is read. Running from a temp
     directory with no repo checkout covers this.

  No network and no real credentials.

## 3. CI workflow (`.github/workflows/ci.yml`)

- **Triggers:** pull requests and pushes to `main`. Add `concurrency` with
  `cancel-in-progress` for the same ref. Set `permissions: contents: read` at
  the top level.
- **Job `check`** (ubuntu-latest):
  - checkout, then `oven-sh/setup-bun` pinned to the Bun version in
    `package.json`/docs;
  - `bun install --frozen-lockfile`;
  - `format:check`, `lint`, `typecheck`, `test:unit`, `test:integration`,
    `build`, `pack:check`.
- **Job `smoke`:** matrix of Node `22` (the minimum) and `24` (current LTS)
  on ubuntu-latest, plus Node 22 on `windows-latest` and `macos-latest`.
  - It runs the packed-tarball smoke test.
  - On Windows, check path handling (`~/.config` / `XDG_CONFIG_HOME`
    fallback, file permission calls that are no-ops there) and fix real
    defects. If Windows support turns out impractical, drop it from the
    matrix and document it as unsupported instead of leaving CI red.
- Every step must fail the job on error. No `continue-on-error`, no `|| true`.
- Pin third-party actions to full commit SHAs with a version comment.
  `actions/*` may be SHA-pinned too, for consistency.
- Cache only Bun's install cache, keyed on `bun.lock`.

## 4. Publish workflow (`.github/workflows/publish.yml`)

- **Trigger:** `push` of tags matching `v*`. Never on PRs or branches.
  `permissions: {}` at the top level.
- **Job `verify`** (`contents: read`):
  - check out the tag;
  - validate the tag against strict SemVer (`vMAJOR.MINOR.PATCH` with an
    optional `-prerelease`), and confirm the tag minus `v` equals
    `package.json` `version`;
  - fail if `license`/`repository` metadata is missing;
  - fail if `npm view <name>@<version>` already exists (don't overwrite);
  - run the full `check` (frozen install, all tests, build, pack check,
    smoke on Node 22);
  - upload the exact `.tgz` as an artifact and record its sha256.
- **Job `publish`** (`needs: verify`; `environment: npm` so a maintainer can
  add a protection rule; `permissions: contents: read, id-token: write`
  **only here**):
  - download the artifact and verify the sha256;
  - set up Node with `registry-url: https://registry.npmjs.org`;
  - make sure the npm CLI version supports Trusted Publishing (verify the
    current minimum in npm's docs; upgrade npm in the job if needed);
  - `npm publish <tarball> --access public`, plus `--tag next` for
    prerelease versions. Never put prereleases on `latest`.
  - No `NODE_AUTH_TOKEN` and no npm secrets: authentication is OIDC only.
    Provenance is generated automatically with Trusted Publishing; add
    `--provenance` only if the docs still require it.
- **After publishing:** `npm view <name>@<version>` (allowing for registry
  propagation delay), then a short `$GITHUB_STEP_SUMMARY` with the version,
  dist-tag and tarball hash.
- **GitHub Release** (optional third job, `contents: write` only there):
  create a release for the tag with generated notes.
- The published tarball is the one built and tested from the tag commit in
  `verify`. Don't rebuild it in `publish`.
- Document the one-time npm setup: package settings → Trusted Publisher →
  GitHub Actions, with owner, repository, workflow filename `publish.yml` and
  environment `npm`. Note that the very first publish of a new package may
  need a manual `npm publish` before a Trusted Publisher can be attached;
  check npm's current docs and document the actual requirement.

Do not claim OIDC publishing works. It can only be confirmed by a real
release after the maintainer configures npm.

- **Security scanning:** CodeQL for JavaScript/TypeScript (default setup or a

  patterns). The existing redaction tests stay green.
- **`.gitignore`:** keep it covering `.env*`, `devzy.yaml`, `dist/` and
  `*.tgz`; add anything new the build creates.
- **Contributor files:**
  - `.github/pull_request_template.md` (checklist: checks pass, docs

  - one bug-report issue template asking for version, Node version, OS,

  - a short `CONTRIBUTING.md` (setup, scripts, commit convention, how
    providers are added, linking the README section).

  No badges, social links or support channels that don't exist.

## 6. Production reliability review

Review and fix only concrete defects, each with a regression test:

- unhandled rejections and uncaught exceptions at the top level: one clear
  error line plus exit 1, no stack trace unless `DEVZY_DEBUG=1` (add that
  flag only if needed, and document it);
- stdout flushing and exit codes under Node (decision 5);
- `EPIPE` when output is piped to `head`: exit quietly;
- non-TTY output: no prompts and no ANSI codes;
- config writes on Windows: the `0600`/`0700` modes are best-effort there,
  so document it and make sure nothing throws.

Do not refactor providers, aggregation or reporting. Do not claim any live
provider was validated against a real service: the tests use stubbed HTTP.
